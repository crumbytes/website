## Proposed configuration

**Vercel:** new dedicated `crumbyte-hub-staging` project in a verified team; root `hub`, Other framework, Node `24.x`, `npm ci`, no build/output override, function entry `hub/api/index.js`, source outside root disabled, no directory listing, automatic domain assignment off. Git auto-deploy stays disabled. Establish protection covering preview/custom/immutable URLs before the first deployment. Read back actual settings; do not weaken protection for tests. Use the prepared project/deployment JSON and validators in `hub/staging/`. Deployment must pin the approved full SHA and `prj_...` ID; omit `target` (Preview). Never select Production.

**Database:** provision only a separately approved NEW `crumbyte-hub-staging` project under the supplied Supabase org. Verify PostgreSQL 17, region, backups (minimum seven days), cost, network restrictions and capacity first. Prefer the documented IPv4-capable shared transaction pooler on explicit port 6543, login `hub_runtime.<NEW-REF>`, database `postgres`; do not invent the region/pooler hostname or ref. Set host/database/ref pins independently from the URL. TLS `sslmode=verify-full` is mandatory. A fixed-egress design and restricted PostgreSQL/pooler access require approval and connection testing. Network restrictions do **not** cover Supabase HTTPS Data APIs: disable unused Data API/exposed schemas, Auth, Storage and external integrations as supported, and verify anonymous HTTPS APIs cannot expose Hub tables/functions. Never put service-role, migration owner or postgres-admin credentials in runtime. Pool limits must fit the approved Micro/project budget, including concurrent serverless instances.

Use the direct owner endpoint from an approved IPv6-capable migration runner where available. Vercel is IPv4-only; its runtime can use the shared pooler without buying a direct IPv4 add-on. Direct migrations may require an approved alternative runner or separately quoted IPv4 add-on. Do not assume a transaction pooler supports owner/migration behavior.

**Migrations:** only after separate hosted migration approval, snapshot the new project, single-operator apply the four ordered `db/migrations/` files using the separate owner connection, verify history/checksums/schema, runtime grants/RLS and owner rejection, then provision only synthetic staff/client A/client B. Migration SQL was exercised on disposable local/CI PostgreSQL; Supabase-specific owner privileges and pooler behavior remain a gate. Runtime URL uses the non-owner `hub_runtime` SQL role. Confirm backup restoration into another isolated destination under separate approval; no automatic down migrations. Keep claim/revocation/audit history during rollback; use an approved compatible build or authorized restore.

**Authentication:** recommend a separate Auth0 Regular Web Application with mandatory MFA, code + S256, approved asymmetric signing and `client_secret_post`. Exact callback `https://hub-preview.crumbyte.com/auth/callback`; exact origin `https://hub-preview.crumbyte.com`; no wildcard. If required, logout allowlist is `https://hub-preview.crumbyte.com/login`; current logout revokes the Hub session, not upstream SSO. Verify tenant policy and signed `amr` includes `mfa` in real positive/negative flows. Prefer TOTP/WebAuthn where entitled. Local OIDC tests do not prove provider policy. No production StackLTR credentials or real customer identities.

**Variables/secrets:** use `hub/.env.example` and staging preflight for the complete list: staging environment/origin, pinned issuer/client ID, confidential OIDC secret, runtime-only DATABASE_URL, independent database host/name and NEW Supabase ref pins. Set all live integrations/jobs off. Supply secrets only to the dedicated project's Preview scope through secure settings. Owner/provisioning credentials remain operator-only. Run offline preflight before deployment, then actual role/TLS/provider checks after approval. Never deploy the local sign-in stub.

External CMS operations remain disabled. Independent penetration testing/manual screen-reader certification and managed-provider acceptance were not performed.
